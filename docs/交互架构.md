# 情感陪伴记忆系统架构

> 适用项目：FurryHeart（ESP32 语音情感陪伴设备后端）
> 核心设计原则：**情感连续性 > 信息检索精度**

---

## 一、全链路数据流

```
ESP32 用户说话
    │
    ▼
[ASR] 语音 → 文字
    │
    ▼
[Orchestrator] ── 1st LLM call (with tools: select_scene + search_memory)
    │
    ├─ tool_call select_scene(scene_id)
    │    → 加载场景提示词
    │    → 2nd LLM call (无 tools)
    │    → 流式输出 token
    │
    ├─ tool_call search_memory(query)
    │    → 向量检索历史会话
    │    → 拼结果到上下文
    │    → 2nd LLM call (无 tools)
    │    → 流式输出 token
    │
    └─ 直接输出 token（无工具调用）
         → 普通闲聊/问候
    │
    ▼
[TTS 流] ── 消费 token 流
    ├─ 检测 [END] → goodbye[0]=True，剥离标记
    ├─ 切句 → 逐句合成语音 → yield PCM
    └─ 尾部残余也送 TTS
    │
    ▼
[WebSocket] ── 逐块发回 PCM 音频
    ├─ audio_stream_end
    └─ (若 goodbye) → goodbye 信号 → ESP32 回到唤醒状态
    │
    ▼
[异步] ── 会话结束，提取记忆
    ├─ LLM 提取会话日记 → 写 sessions 表 + 生成 embedding
    ├─ LLM 更新用户档案 → 写 users 表
    └─ 清理过期 upcoming_events
```

---

## 二、记忆系统：双通道架构

情感陪伴的记忆需求分两类，走不同技术路径，互不冲突。

```
┌─────────────────────────────────────────────────────────────┐
│                    双通道记忆架构                            │
│                                                             │
│  通道一：记忆注入（底色）        通道二：向量检索（搜索引擎） │
│  ────────────────────────        ─────────────────────────   │
│  时机：会话开始时注入一次         时机：LLM 按需调用 tool      │
│  方式：拼入 system prompt        方式：search_memory 工具     │
│  内容：                           内容：                      │
│    • 用户档案 (profile)            • 超出10条窗口的旧会话     │
│    • 最近10条会话 (sessions)       • 语义检索，不按时间排序   │
│    • 待发生事件 (upcoming)         • 返回 top-3 + 阈值过滤    │
│    • 环境信息 (日期+天气)                                    │
│  用途：情感连续性、主动关怀        用途：用户明确追溯旧事       │
│  特点：老朋友自然记得你的事        特点：你想起来再去翻         │
│  覆盖：~90% 需求                  覆盖：~10% 需求             │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 通道一：记忆注入（会话开始时一次性注入）

每次 WebSocket 连接建立时，从 SQLite 读取记忆，拼入 system prompt。
LLM 每轮对话都能看到，不需要每句重复注入，也不需要检索。

```
system prompt 最终结构（从上到下）：

今天是2026年5月6日，星期三。南京，晴，26°C。    ← 环境信息（纯代码获取）

《历史记忆》
                                        ← 通道一：记忆注入
【用户档案】
小明，男，大二，南信工 电子信息工程
性格偏内向，敏感
爱好：打游戏、看书

【最近的对话记录】
5月5日（低落）：
- 老板在周会否定了他的方案，很委屈
- 下周末要和初中同学吃烤羊腿，期待

【即将发生的事】
- 明天(5.8)：和初中同学吃烤羊腿
- 暑假(7-8月)：女朋友小红来南京

【刚过去的事】
- 5月5日：烤羊腿 → 可主动问问

                                        ← base.txt 人格设定
你是绒绒心语，一个温暖贴心的AI情感陪伴伙伴...
（以下省略）

                                        ← 场景/工具指引
## 场景工具
你可以调用 select_scene 工具...

## 记忆搜索
当用户明确提到旧事时，调用 search_memory 工具...

## 结束对话
确定用户想结束时，在回复末尾加 [END]...
```

### 2.2 通道二：向量检索（按需触发）

```
用户："还记得我之前说的那个面试的事吗？"
                        │
                        ▼
LLM 检查上下文 → 最近10条没有面试相关内容
                        │
                        ▼
LLM 调用 search_memory(query="面试的事")
                        │
                        ▼
服务器：embed(query) → SQLite 全量算余弦 → top-3 相关会话
                        │
                        ▼
拼入上下文 → 2nd LLM call → 自然回复
```

**为什么没有"鸡生蛋"问题？** 触发条件是用户**明确表达了追溯意图**（"还记得…吗""上次说的…"），不是 LLM 凭空猜测这时候该搜什么。

### 2.3 记忆写入时机

```
会话结束（[END] 触发）
    │
    ├── 1. LLM 提取会话日记 (events + emotion + upcoming)
    │      → 写入 sessions 表
    │      → 写入 upcoming_events 表
    │      → events 文本拼成一段 → 调 embedding API → 存向量
    │
    ├── 2. LLM 提取/更新用户档案 (profile)
    │      → 读取当前 profile_json
    │      → LLM 输出更新后的 JSON → 写回 users 表
    │
    └── 3. 清理过期 upcoming_events
           → 纯代码逻辑，按日期算状态流转
```

### 2.4 存储结构

```sql
-- 用户档案（结构化 JSON，累积更新）
CREATE TABLE users (
    user_id      INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id    TEXT UNIQUE NOT NULL,
    profile_json TEXT DEFAULT '{}',       -- JSON: name, age, city, hobbies...
    created_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at   DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 会话日记（事件级细节，每次对话一条）
CREATE TABLE sessions (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id  TEXT NOT NULL,
    date       TEXT NOT NULL,              -- "2026-05-06"
    emotion    TEXT,                       -- "开心"/"低落"/"焦虑"...
    events     TEXT NOT NULL,              -- JSON array of strings
    embedding  TEXT,                       -- JSON float array, 向量检索用
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 待发生事件（带预估日期，独立维护）
CREATE TABLE upcoming_events (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    device_id   TEXT NOT NULL,
    content     TEXT NOT NULL,
    est_date    TEXT NOT NULL,              -- "2026-05-08" 或 "2026-07"
    precision   TEXT DEFAULT 'day',         -- "day" / "month"
    source_date TEXT NOT NULL,
    status      TEXT DEFAULT 'pending',     -- pending / passed / expired
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

## 三、Tool 系统

只定义两个 tool，轻量精准，不做 MaiBot 那种多 tool 编排。

### 3.1 select_scene — 场景化提示词

```python
SCENE_TOOL = {
    "type": "function",
    "function": {
        "name": "select_scene",
        "description": "根据用户当前的情感状态和话题，选择最匹配的情感场景，获取该场景的专属回复指南。当用户表达了明确的情绪困扰、工作压力、家庭矛盾等话题时调用。",
        "parameters": {
            "type": "object",
            "properties": {
                "scene_id": {
                    "type": "string",
                    "enum": [
                        "daily",                    # 日常闲聊
                        "work/pressure",            # 工作压力/加班
                        "work/conflict",            # 职场冲突
                        "work/career",              # 职业困境
                        "emotion/loneliness",       # 孤独感
                        "emotion/relationship",     # 感情问题
                        "emotion/anxiety",          # 焦虑/内耗
                        "family/origin",            # 原生家庭
                        "family/expectations",      # 家庭期望
                    ],
                    "description": "最匹配的情感场景ID",
                }
            },
            "required": ["scene_id"],
        },
    },
}
```

**设计理由**：场景化提示词让 LLM 的回复风格随用户情绪自适应。用户说"今天好累"和"周末要去吃烤羊腿"，LLM 应该用完全不同的语气和策略回应——场景工具就是为了这个。

### 3.2 search_memory — 向量检索历史记忆

```python
SEARCH_MEMORY_TOOL = {
    "type": "function",
    "function": {
        "name": "search_memory",
        "description": "搜索用户的历史记忆。当用户明确问到以前说过的事、让你回忆过去聊过的内容时调用。例如：'还记得我之前说的...'、'我上次提到过...'",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {
                    "type": "string",
                    "description": "搜索关键词或简短描述，表达你想找什么内容的记忆",
                }
            },
            "required": ["query"],
        },
    },
}
```

**设计理由**：
- 只用语义向量检索，不用关键词匹配——用户说"面试的事"可能匹配到3个月前的"面试焦虑"，关键词搜不到
- 返回 top-3 + 阈值过滤（0.5），质量不够就不返回
- 检索范围排除最近10条（已注入不需要再搜）
- 不需要 BM25、图关系、PageRank——单用户场景几百条数据，全量余弦算一遍 < 5ms

### 3.3 [END] — 结束对话标记

[END] 不是 tool，是嵌入在 system prompt 中的一段指引：

```
## 结束对话
当你判断用户想结束对话时（比如用户说了再见、拜拜、晚安、不聊了、
我去忙了，或者语气暗示想结束），你正常回复一句自然的告别，然后
在回复的最末尾加上标记 [END]。注意：[END] 不会被用户听到，它
只是给系统的信号。只在你确定用户想结束时才加。
```

**处理流程**（在 TTS 层完成，不需要 LLM 参与）：

```
LLM 输出 token 流
    │
    ▼
TTS return_audio_generator()
    ├─ 逐 token 累积到 sentence_buf
    ├─ 检测到 [END] → goodbye[0]=True, 剥离标记, 停止消费
    ├─ 剩余文本当最后一句合成
    └─ 尾部残余也送 TTS
    │
    ▼
WebSocket 发送 → audio_stream_end → (goodbye) → goodbye 信号
```

**为什么不把 [END] 做成 tool？**
- [END] 不是"决策"而是"信号"——LLM 不需要思考"要不要调 end_conversation 工具"，只需要在告别话末尾加个标记
- 做成 tool 会增加 LLM 一次调用（tool_call → tool_result → continue），增加延迟
- 标记在 token 流中边消费边检测，零额外延迟

## 四、与 MaiBot 的关键差异

| 维度 | FurryHeart（本方案） | MaiBot |
|------|---------------------|--------|
| **记忆哲学** | 注入为主，检索为辅 | 纯检索（无注入机制） |
| **覆盖策略** | 通道一注入 90%，通道二检索 10% | 100% 靠检索 |
| **tool 数量** | 2 个，轻量精准 | 12 个，两阶段编排 |
| **Timing Gate** | 不需要（硬件唤醒词代替） | 需要（群聊判断要不要回） |
| **向量检索** | API + SQLite + 全量余弦 | Faiss SQ8 + BM25 + 图谱 |
| **复杂度** | 低，一人可维护 | 高，需理解多种检索引擎 |
| **适用场景** | 单用户设备端情感陪伴 | 多平台群聊机器人 |

**核心差异一句话总结**：MaiBot 不知道谁会在什么时候说话，所以它需要复杂的检索 + 门控来判断"要不要回"和"回什么"；你的 ESP32 设备有唤醒词和硬件绑定，天然知道"用户在跟我说话"，所以可以把精力全部放在"怎么回得更温暖"上。
